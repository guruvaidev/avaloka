Start here

Python 3.11 or 3.12. From a checkout: pip install -e .; then:

$ avaloka analyze app/sample_data/salaries.csv --goal "what drives salary here?"
$ avaloka train   avaloka/examples/churn.csv --target churned
$ avaloka chat    avaloka/examples/churn.csv

Everything runs locally by default and your data stays on your machine. Every run writes a bundle: an executive report, a README of findings and limitations, and the code that reproduces the run.

avaloka coordinate

Multi-Avaloka — one main Avaloka fans a fleet of self-clones across the same dataset (each runs its own swarm on a shard) and converges one answer.

The clones' answers to the goal are merged from their sufficient statistics (sums and counts add, means are weighted by rows), each clone's share is cited by its row range, and a figure that cannot be merged exactly (a median) is labelled approximate. The answer is printed and written to <output>/goal_analysis.json and <output>/executive_report.md.

The source may live anywhere: a local file, a database table/query or cloud object storage — it's resolved to a local file before the fleet is dispatched.

Every clone's work is traced separately: <output>/swarm_trace.json holds one record per clone step (what it received, each firefly's output and cost, what it returned, whether the merge selected it) and <output>/swarm_trace.jsonl streams the same records live, one per line, so another process can tail it.

Three levels of narration. Default: results only. -v: the team's story — who took which shard and what each clone came back with. --debug: every specialist step inside every clone, with its own one-line output. Every sentence is produced from a trace record, so what is printed is what ran.

Debug narration: how the team worked

avaloka coordinate is a team: one coordinating Avaloka reads the data, cuts it into shards and hands each to a clone; each clone runs her own specialists (a data scout, a sampling specialist, a data engineer, an analysis planner, a validator, a reporter) on her shard; the coordinator merges what they bring back. Three levels of narration say how much of that you see.

defaultResults only: the converged profile, the fleet table, the verdict, the economics and the bundle path.
-v, --verboseThe team's story as it happens: the brief, the shards, each clone leaving and returning, the merge and the close.
--debugEverything -v says, plus every specialist step inside every clone with that step's own one-line result. Local output only; it may show your column names.

Every sentence is produced from one record of the swarm trace (swarm_trace.jsonl) at the moment it is written, by avaloka/swarm_narration.py. There is no script to fall back on: a line that is not in the records is not printed, and the file and the screen cannot disagree.

Swarm size and the cap

--swarm N (short -s; --workers/-w is the same option under its old name) is the number of clones. Unset, it is 4 or your edition's cap, whichever is lower. The cap lives in avaloka/swarm_limits.py: Swarm on the free open-source edition: up to 2 clones per mission, run locally. Professional allows 16; Enterprise has no limit. Ask for more than the cap and the run proceeds at the cap, saying so once:

$ AVALOKA_EDITION=oss avaloka coordinate data.csv --goal "…" --swarm 5
Swarm limited to 2 clones on the free open-source edition: you asked for 5, so 2 will run.

With --debug the narration also states the effective team size and the cap it sits under. Nothing else is said about editions.

Formats and sources

Any command that takes a dataset accepts these file formats (avaloka/io/loader.py):

FormatSuffixesNotes
CSV, TSV, TXT.csv .tsv .txtdelimiter sniffed for .csv/.txt; header found below a title block
Parquet.parquet .pqread with pyarrow
JSON.jsonrecords, or nested objects flattened with a separator
JSON Lines.jsonl .ndjsonone record per line
XML.xmlrepeated elements become rows
ORC.orcread with pyarrow

Excel.xlsx .xlsm .xlsfirst sheet, header found below a title block

A directory of part files — one Spark or Daft output written as many files — is read as one dataset when every part has the same suffix, one of .avro .csv .json .jsonl .ndjson .orc .parquet .pq .tsv .xml; _SUCCESS and hidden files are ignored.

Model providers (--llm)

Without --llm nothing leaves your machine. With it, Avaloka's lines are reworded by a model; the numbers still come from the statistics and a rewording that changes one is discarded. Choose the provider with --llm-provider or AVALOKA_LLM_PROVIDER (the flag implies --llm) and the model with --llm-model or AVALOKA_LLM_MODEL. With neither, the first configured provider in this order is used (avaloka/llm/providers.py):

The first four speak the OpenAI-compatible chat API; Anthropic goes through its own SDK (pip install 'avaloka[llm]'). A provider that is named but unusable, or that fails mid-run, prints one line naming the provider and the fix, and says the rest of the run uses Avaloka's deterministic wording:

LLM error (groq): Groq rejected the API key (HTTP 401). Fix: check GROQ_API_KEY, or choose another provider with --llm-provider. Continuing without the model: the rest of this run uses Avaloka's deterministic wording.

Starting the API

The CLI is standalone and needs no server. The platform's HTTP API (upload → chat → assets → models, the agent trace, the swarm missions) is a separate process from the same repository:

$ pip install -r requirements.txt
$ uvicorn app.api.server:app --port 9000 --loop asyncio   # the API
$ docker compose up -d                          # optional: the Milvus stack

See docs/api.md for the endpoints and docs/INSTALL.md for the full install, including Kubernetes. avaloka benchmark serve above is the only server the CLI itself starts, and it binds loopback only.
