Avaloka 1.6 · Apache-2.0

Build on an AI data scientist that checks its own work.

Avaloka turns a dataset and a question into an answer you can defend: the analysis, the code that produced it, a validated model when you need one, and the evidence behind every number. This guide shows you how to use it, and how to build it into your own tools.

Python 3.11 · 3.12 Runs locally, no API key Ray & Kubernetes when you scale

Four ways in

Every surface drives the same engine. Pick the one that matches where your work happens.

Command lineavaloka analyzePoint it at a file and ask a question. The fastest way to a real answer. Python SDKrun_analyze(ctx)Run missions from scripts, notebooks and pipelines and get structured results back. HTTP APIPOST /threads/…/messagesPut the conversational agent team behind your own product or UI. Model servicePOST /predictEvery trained model ships with a typed REST service you can run anywhere.

What you can rely on

  • Numbers come from code, not from a language model. Every figure is computed by Python you can read, rerun and hand to someone else.
  • It says when it can't answer. If your question names a column that isn't there, you get LIMITED and the reason, not a confident guess.
  • Models have to earn trust. A model is compared against a trivial baseline, and production deployment always needs a human to approve it.
  • Your data stays where you put it. The CLI and the SDK run on your machine. Nothing leaves it unless you configure a hosted model provider.

Five minutes

Quickstart

You need Python 3.11 or 3.12 on macOS or Linux. No API key and no services.

  1. Install

    git clone https://github.com/guruvaidev/avaloka.git && cd avaloka
./scripts/install.sh && source .venv/bin/activate

    The installer creates .venv, installs everything, and finishes by checking your environment. It takes 5–10 minutes and ends with Everything checks out.

  2. Ask your first question

    avaloka analyze app/sample_data/healthcare_dataset.csv \
        --goal "average billing amount by medical condition"
    What I found
  • Medical Condition=Obesity: mean Billing Amount=2.58e+04.
  • Medical Condition=Diabetes: mean Billing Amount=2.56e+04.
  • Medical Condition=Asthma: mean Billing Amount=2.56e+04.
  • Medical Condition=Arthritis: mean Billing Amount=2.55e+04.
  • Medical Condition=Hypertension: mean Billing Amount=2.55e+04.

Validation verdict: PASS; max safe deployment level 1/4
Deliverables → avaloka-analysis/acec94262892
  open avaloka-analysis/acec94262892/executive_report.html   the decision summary
  cat  avaloka-analysis/acec94262892/README.md               findings and limitations
  python avaloka-analysis/acec94262892/analysis.py           reproduce this run

  3. Train a model, or talk it through

    avaloka train app/sample_data/yellow_tripdata_2015-01_dataset_50k.csv --target payment_type
avaloka chat  app/sample_data/healthcare_dataset.csv

    train fits several candidate models, keeps the one that beats the baseline by more than fold noise, and writes a deployable package. It takes about 2 minutes. chat reads the file, says what it notices, and offers numbered next steps you answer with a number.

Optional: add a model key

The CLI and SDK need no key. Set OPENROUTER_API_KEY, GROQ_API_KEY or OPENAI_API_KEY, or use a local Ollama with INFERENCE_PROVIDER=local, when you want the conversational agent team behind the HTTP API.

Concepts

How Avaloka works

Five ideas explain almost everything you'll see: missions, the team that runs them, the lane a job runs in, the checks a result must pass, and the verdict it ends with.

Missions

A mission is one unit of work with a goal, a dataset, a budget and an output folder. Avaloka doesn't hand you a chat reply. It hands you a finished bundle: a report, the code, the data it actually used, and a record of every check.

MissionYou give itYou get back
Analyzea dataset and a goalfindings, an executive report, reproducible code and a notebook
Traina dataset and a target columneverything above, plus a validated model, a model card and a deployment package
Deploya trained package and a levela gate check and the exact commands to ship it

Every mission carries a budget. It's a hard ceiling: when the next step would cross it, Avaloka stops and tells you, instead of overspending.

The team

Work is done by a small team of specialists. The Planner leads it. You talk to the Planner, and it decides who does what.

LeadPlannerUnderstands your request in the context of your data, asks when something is ambiguous, proposes a plan, and asks for your go-ahead before anything expensive such as training or a cluster job. Then it hands each step to the right specialist and brings the results back to you.
LookSampling · ProfilingRead the schema, profile every column, flag quality problems.
WriteCoderPlans the steps in plain language, then writes Python that follows them.
CheckValidatorChecks syntax, schema and logic before any code runs.
RunExecutionRuns on your machine, as a Kubernetes Job, or on Ray.
LearnModel TrainingTrains candidates and tracks them in MLflow.
ShowVisualizationTurns results into charts and a report.

What this means for you:

  • You can be vague, and it will ask. A request it can't act on safely gets a clarifying question, not a guess.
  • Expensive steps wait for you. Ask to train a model and the first reply is a plan, with the target, features, excluded identifier columns and settings. Training starts only when you confirm.
  • You can see the plan. The plan, the code and the execution context come back in every API response, so your UI can show the user what's about to happen.

Workload lanes

Before touching the data, Avaloka sizes the job by reading the file size and estimating the row count. It then chooses a lane and tells you which one it picked.

LaneWhenWhat happens
onlineup to 100k rows / 50 MBThe whole dataset is analysed live.
sampled_onlineup to 5M rows / 1 GBA statistically sound sample now, plus an offer to run the full pass.
batchlarger than thatA full pass as a Ray job, locally or on Kubernetes, with exact results and no sampling error.

The evidence layer

Three checks stand between a result and you:

  • Integrity refuses to train on leaked targets or on train/test splits that share rows. Identifier-like columns such as customer_id are left out of the features.
  • Evaluation compares every model with a trivial baseline, such as always predicting the most common class. A model that doesn't beat it is reported as such.
  • Claim verification checks the written summary against the computed numbers. It's deterministic and uses no language model.
Check the evidence fields, not just the prose

The CLI and SDK refuse to call a model trustworthy unless it beats its baseline. Over the HTTP API, read evaluation_beats_baseline and verification_safe_to_present in the response before you present a model or a narrative to your users. Treat the fields as the source of truth.

Verdicts and deployment levels

Every mission ends with a validation verdict and the highest deployment level its result can safely claim.

PASS all checks passed   WARN usable, with caveats it lists   FAIL don't rely on it

1Research artifactmodel file and model card
2Deployment packageAPI, container, schema, tests, lock file
3Staging-readymanifest, monitoring, registry descriptor
4Production candidateclean validation and human approval

Analysis missions stop at level 1. The validator caps the level a model can claim, and level 4 always needs an explicit approval. Avaloka never promotes a model to production on its own.

Working with data

Formats

FormatExtensionsNotes
Delimited text.csv .tsv .txtDelimiter and encoding are detected. A TSV that parses as one column is re-read.
Columnar.parquet .orc .avroTypes are kept as stored.
Spreadsheets.xlsx .xlsm .xlsThe header is found below title rows; see below.
Documents.json .xmlRead when there's one sensible table. XML with a DTD is refused.

Spreadsheets as people make them

  • Title rows, blank rows and notes above the table are skipped. The real header row is found.
  • A header split over two rows, such as a Q1 / Q2 band above Revenue / Cost, becomes one set of column names.
  • Subtotal and grand-total rows aren't counted as data. If a statement's totals are kept as rows, the result says so.
Multi-sheet workbooks

In 1.6 the upload path reads the longest sheet, which may not be the one your question is about. Upload the sheet you mean on its own.

Missing values

Words like None, NA and N/A mean missing in a numeric column, but in a text column they're kept as categories. A category literally called "None" stays a category. The exact rule that was applied is recorded with every read, so you can always see which values were treated as missing.

Answered or limited

goal_analysis.json says whether your question was actually answered. The same goal can go either way depending on whether it names something the data has. The churn example has a monthly_charges column but no monthly_spend:

{
  "status": "answered",
  "kind": "group_comparison",
  "scope": "All 1,200 working rows",
  "findings": [
    "region=south: mean monthly_charges=71.2.",
    "region=east: mean monthly_charges=68.8.",
    "region=west: mean monthly_charges=68.1.",
    "region=north: mean monthly_charges=67.7."
  ]
}
{
  "status": "limited",
  "kind": "group_comparison",
  "scope": "All 1,200 working rows",
  "metrics": {
    "group_column": "region",
    "value_column": null,
    "unresolved_measure": { "statistics": ["mean"], "measure": null, "candidates": [] }
  },
  "findings": [
    "The goal asks for mean, but names no numeric column to calculate it from. Name the column in the goal to get a figure."
  ]
}

Treat LIMITED as a prompt to rephrase, not a failure. When several columns could match (gross_revenue, net_revenue), they're listed in candidates so you can pick one.

Economics

Each mission closes with an economic summary in economics.json: duration, compute and model cost, the estimated manual effort it replaced, and the human review it still needs. Local missions cost nothing. The effort estimate is a conservative heuristic, so read it as a rough guide, not a measurement.

Analyse a database table

avaloka analyze 'sqlite:////data/app.db#customers' --goal "average monthly_charges by region"
avaloka analyze 'sqlite:////data/app.db#query=SELECT * FROM customers WHERE churned = 1' --goal "average monthly_charges by contract"

The table, or the query result, is copied to a local Parquet file and analysed like any other file. Any SQLAlchemy URL works the same way; install its driver first.

Keep a run inside a budget

avaloka train customers.csv --target churned --max-cost 25 --deployment-latency-ms 100

The budget decides how many candidate models are tried. The run also writes cost_quality.json, with Economical, Balanced and Maximum-quality options, their serving costs, and a recommendation.

A file too big to analyse live

avaloka batch transactions.parquet --target kubernetes --apply     # submit as a KubeRay RayJob
Exact rows analysed: 50,426 (no sampling — partial sums combined losslessly).

Python SDK

The CLI is a thin layer over a Python API you can call directly. Missions run in-process, on your machine, and return structured results.

Run a mission

from pathlib import Path
from avaloka.mission.budget import Budget
from avaloka.mission.context import MissionContext, MissionKind
from avaloka.missions import run_analyze

Budgets

from avaloka.mission.budget import Budget, BudgetExceeded

budget = Budget(limit_usd=1.0)
try:
    budget.spend(2.5, "hyper-parameter search")
except BudgetExceeded as err:
    print(err)
Action 'hyper-parameter search' costs $2.50 but only $1.00 of the $1.00 budget remains. Avaloka refuses to proceed rather than overrun the declared budget.

HTTP API

The API puts the conversational agent team behind your own product: upload data, open a thread, send messages, and collect the code, results and models it produces. It's what the Avaloka web app uses.

Run it

The API needs Redis for session storage and the LangGraph server for the agent graph. The Helm chart deploys both. To run them locally:

docker compose -f deploy/compose/docker-compose.redis.yml up -d
export REDIS_URL=redis://127.0.0.1:6379
export OPENROUTER_API_KEY=…                       # or GROQ_API_KEY / OPENAI_API_KEY
export MLFLOW_TRACKING_URI=sqlite:///$PWD/mlflow.db   # needed for training
export SUPABASE_JWT_SECRET=$(openssl rand -hex 32)

langgraph dev --no-browser --port 2024 &
uvicorn app.api.server:app --port 9000
{"status": "ok", "graph_ready": true, "upstream_reachable": true, "redis_connected": true, "redis_mode": "single"}
Readiness is in the body

/health returns 200 even when Redis or the graph server is down. Check redis_connected and upstream_reachable. Interactive docs are served at /docs.

Authentication

Every route except /health and /version needs Authorization: Bearer <jwt>. The token's sub is the user id; make it a UUID.

  • With Supabase Auth (the web app): send the signed-in user's access token. RS256/ES256 tokens are verified against SUPABASE_URL's key set.
  • Server to server: sign an HS256 token with the same SUPABASE_JWT_SECRET the server reads. The server refuses to start without that secret.
import os, time, uuid, jwt   # PyJWT

token = jwt.encode({"sub": str(uuid.uuid4()), "iat": int(time.time())},
                   os.environ["SUPABASE_JWT_SECRET"], algorithm="HS256")
auth = {"Authorization": f"Bearer {token}"}
// In the browser, use the Supabase session's access token:
const { data: { session } } = await supabase.auth.getSession();
const auth = { Authorization: `Bearer ${session.access_token}` };
export JWT=$(python -c 'import jwt,os,time,uuid; print(jwt.encode({"sub": str(uuid.uuid4()), "iat": int(time.time())}, os.environ["SUPABASE_JWT_SECRET"], algorithm="HS256"))')
curl -s localhost:9000/debug/whoami -H "Authorization: Bearer $JWT"   # {"user_id": "8c6943d7-…"}

Ask a question

POST/threads/{thread_id}/messages

Send a message in a thread. The call returns when the turn finishes, typically in 10–40 seconds for an analysis question.

reply = requests.post(

What comes back

Every turn returns the full state of the conversation. These are the fields most integrations use:

FieldUse it to
messagesShow the conversation. The last message is the reply.
coder_definition.codeShow or store the Python that produced the answer.
output_file_dataOffer the result table as a download (base64 data URL).
visualization_configRender charts of the result.
planner_definition, execution_contextShow what the team planned and how it ran: locally, on a sample or the full file, or on a cluster.
verification_safe_to_presentDecide whether to present the narrative as is.
training_status, training_completed, mlflow_run_idFollow a training run.
evaluation_beats_baseline, integrity_safe_to_trainDecide whether a trained model is worth using.
agent_errorsShow what went wrong when a turn fails.

Model service

A train mission run with --deployable writes service.py, a small FastAPI app that loads the validated model, plus a Dockerfile and manifests. It's yours to run anywhere and safe to edit.

GET/health

POST/predict

Send rows as instances. inference_schema.json in the package lists the exact features and types the model expects.

{

{"predictions": [1], "model_version": "46f6dfcc2c31", "probabilities": [0.913]}

probabilities is the positive-class probability and is returned for binary classifiers.
