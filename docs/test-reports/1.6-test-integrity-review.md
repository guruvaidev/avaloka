# Test integrity review — closing 1.6

October 2026, against `develop-1.6`. Every number below was produced by running
the thing it describes, in the CI container (`avaloka-ci-deps`, Python 3.11,
git and Helm v4.2.3 installed so the contract suite and the rendered-chart
contract run rather than skip). Gate means
`pytest tests/ -m "not cluster and not cloud and not integration"`.

**Read these as a dated snapshot.** Totals move with every merge; the named
defects, the named tests and the reasoning are the durable part. A count is
comparable only against the base commit run in the same container on the same
day, which is how every before/after below was taken.

## The short version

The review asked four things: remove tests that pass without testing anything,
make execution results visible the same way on every backend, find where the
model-training agent actually joins the product, and turn mock-only
"integration" tests into real ones. It also asked why spreadsheet uploads fail
on ordinary messy files.

One pattern explains most of what was found:

> **A one-sided check fails as a plausible wrong result, not as no result.**

A status check that only fires when a status is present records a run with no
status as a success. A test whose `except` swallows its own assertion records a
failure as a pass. A spreadsheet reader that never asks whether a row is a total
reports a clean read with every sum doubled. Each of these looks exactly like a
working control until something is mutated and nothing goes red.

The second pattern is **capability that exists, is tested, and is not called.**
Four instances in the spreadsheet subsystem alone: the table-shape reader on
the upload path, its own symptom detector, a multi-table loader, and the
shape report. All four had tests. None had a production caller.

## 1. Tests that passed without testing

| Shape | Where | Why it could not fail |
|---|---|---|
| Assertions inside `try: … except Exception: print("✗ FAILED"); return False` | `tests/test_inference_integration.py` | `AssertionError` is an `Exception`. The test printed "FAILED" and pytest recorded a pass. |
| Called a method the object does not have, accepted the `AttributeError` | two tests in `tests/test_mta_training.py` | Both called v1 methods on the v2 agent. One then passed on a substring match against a *private* method name. Neither reached training code. |
| Constructor raised before the call under test | `test_config_creation_failures` | In three of four branches the `TrainingTask` constructor failed, so the function the test names was never called. |
| Asserted a key that is always present | `test_train_with_classification_plan` | `num_classes` exists for every model type, so any result passed. |
| Asserted only that a dict came back | `test_unknown_tool_skipped` | `execute()` also returns a dict after catching an error. |
| Import check that skips on `ModuleNotFoundError` | `tests/k8s/test_t7_agent_matrix.py` | Catches a *broken* module but not a *deleted* one: removing the package turns 11 tests into silent skips. |

**What replaced them.** Every new or tightened test was run against a mutant of
the code it covers and seen to fail, then seen to pass without the mutant. The
tests they replace passed under every one of those mutants:

| Mutant | Fails |
|---|---|
| graph node returns state untouched | both node tests |
| confirmed plan skips training | the training test |
| `execute()` error handler re-raises | the failed-turn test |
| `execute()` renamed | the entry-point test |
| unknown tool raises | the unknown-tool test |
| trainer reports regression for a classifier | the classification test |

One mutation round itself was caught passing vacuously: `execute()` appends to
the caller's `messages` list in place, so the first version of a test compared
a list with itself. It now compares against a snapshot.

**A limit worth stating.** An automated scan for vacuous tests reported 64,
then 37 once helper chains were followed, then essentially none after each was
read: the clusters delegate to helpers (one ending
`mock_handler.assert_called_once()`) that a module-level scan cannot see
through. A scanner that can only over-report is itself a one-sided check. The
findings above are the ones confirmed by reading and by mutation, not by the
scan.

## 2. Execution results: one design on every backend

**Defect.** The Kubernetes execution node wrote `execution_result` only on its
two pre-flight failures. Once code had been sent to the cluster — success or
failure — the key was left as it came in. Two consequences:

- a successful run on Kubernetes skipped visualisation and narration, because
  both branch on that status;
- a **failed scheduled run on Kubernetes was recorded as a success**. The
  scheduler's verdict (`app/core/celery_app.py`) reads
  `if st and st not in ("success", …)`, so a *missing* status can never produce
  a failure.

Reach was bounded: one API path hard-codes `deploy_on_k8s: False`. It is still
the shape this review is about — the check is correct for every status except
the absent one, which is the one the bug produced.

**Second defect, found on the way.** Four keys the execution nodes write —
`execution_stdout`, `execution_stderr`, `execution_error`,
`fresh_output_produced` — were not declared in the graph state. LangGraph
silently drops undeclared keys from a node's return (measured on 0.6.11), so
every read of `execution_error` through the graph saw nothing. The reads
affected turned out to be redundant second clauses of an `or` whose first
clause already caught the case, so no user-visible behaviour depended on them;
they are declared now so the next reader is not silently wrong.

**Fix.** The Kubernetes node writes the same keys as the local node on every
outcome, and both emit one behaviour-only `execution_result` log line per run,
so a result is visible in `kubectl logs` whether or not it is persisted. Log
lines that carried output paths or result tables were removed rather than
moved. Gate: +52 passed against its base, no new failures.

**Not yet verified:** the Ray execution node received the same treatment and is
covered only by unit tests. It needs one run on a cluster.

## 3. Where the model-training agent joins the product

The graph's `train_models` node calls `model_training_agent_node`, which
`app.agents.model_training_agent` re-exports from **`app/agents/mta_v2`**.
Nothing in production imports `app/agents/mta` (v1). The v1 package is 20
tracked files with 185 tests, 132 of them deselected from the gate; three tests
that exercised the live path were ported to `tests/test_mta_v2_graph_node.py`
before anything else was touched.

Deleting v1 is a separate change and needs one edit made first: the
skip-on-missing import check above, or the deletion reads as 11 skips instead
of a removal.

## 4. "Integration" tests that were neither integration nor running

Thirteen files were named `*_integration.py` while mocking every boundary they
touch. The suffix marks a file `integration`; the gate selects
`not integration`; so **none of them ran anywhere** — not in the gate, not in a
nightly job. They are renamed `*_unit.py` and now run.

Tests in them that fail now that they run are defects the filename was hiding.
No test was skipped, xfailed or edited to make the rename pass.

Three groups turned out to mock their dependency by name while still reaching
outside the process, and were moved back behind the marker verbatim:

| File | What it reached |
|---|---|
| `tests/test_infra_integration.py` (62 tests) | a real `kubectl get nodes`; only 3 tests stub it |
| `tests/test_execution_ssh_integration.py` (3) | a real `scp` to configured hosts |
| `tests/test_mta_v2_flows_integration.py` (1) | an anonymous read from a public object-storage bucket |

The last one was caught by its logs: **12** `Anonymous caller does not have
storage.objects.get` lines appeared in the gate after the first rename, against
0 at the base and 0 after the fix. A hermetic gate making live calls to the
public internet passes as long as the internet answers, which is how it
survived.

**Real integration tests.** `tests/containers/` runs against Postgres 16 and
SeaweedFS 4.48 — the images the Helm chart deploys — started by
`scripts/integration.sh` with credentials generated per run. It also runs the
Postgres half of `tests/test_lineage.py`, which had never run against Postgres.
It cannot pass vacuously: fixtures raise when a container is unreachable, a
conftest hook turns any skip into a failure, and the runner fails on a skip, on
zero tests collected, and on a missing docker. Every test marked `containers`
is also marked `integration`, and a test pins that invariant.

A nightly workflow schedules it. **It has not yet executed**: its first run
needs a manual dispatch.

## 5. Spreadsheet uploads and ordinary messy files

### There are two Excel paths, and they behave differently

- **Browser upload**: every sheet becomes its own dataset.
- **Connector read** (`ExcelConnector.load_dataframe`, used by sampling and data
  transfer): one sheet, chosen as the one with the most rows.

A fix measured on one path says nothing about the other.

### The 20 failures, by cause

`tests/test_spreadsheet_comprehension_upload_path.py` drives realistic bad
workbooks through the upload path. At the start of this review it read
**20 failed, 19 passed**. Each failure traces to one of these causes:

| Cause | Failures | What the user saw |
|---|---:|---|
| Year headers (`Region, 2021, 2022, 2023`) rejected because a year parses as a number | 3 | columns named `column_1…column_4` |
| A merged group label above the column names | 3 | the real column names read as a data row |
| A header written on two rows | 3 | rejected as a "banded data row" because group labels repeat |
| Footnote markers and a notes block under the table | 2 | notes read as records, `*` left on labels |
| A second table below the first | 1 | read as more rows of the first |
| Sheet choice: the biggest sheet is not the one asked about | 5 | the wrong sheet, silently |
| A decoy sheet (lookup or notes tab) larger than the data | 3 | the wrong sheet, silently |

The test file's own docstring attributes the two-row-header case to the
number check; measured, it is the duplicate-label check.

### A sixth defect nobody had a test for: the totals row

A `Total` row under the data left no trace. Right names, right types, a clean
frame, the shape report saying the read was clean, `notes=[]` — and on a
minimal case: 5 rows instead of 4, every sum doubled (Units 2000 for 1000,
Revenue 20000 for 10000), the **maximum equal to the total itself**, and the
mean 4000 instead of 2500. On both paths.

This is the most dangerous kind of bad data because nothing fails: every
downstream chart and insight is wrong, and confidently so.

### How the fixes reason about bad data

The rule throughout: **leave a row out only on evidence, never on
resemblance, and say what was assumed.**

- **A total is decided by arithmetic, the label is only a hint.** The last row
  is a total if it equals the column sums above it. Rows in the middle are
  subtotals only inside a structure that checks itself: each closes its group,
  together they close every record, and a grand total equals the sum of the
  records. A subtotal with no grand total is left in — in a financial statement
  it is a line item — and the user is told it may be counted twice.
- **Notes are notes only if every row reads like one** (a marker,
  `Source:`, a sentence). A checklist whose last items are one cell wide is
  records. `#` is not a footnote marker: `Order #` is a column.
- **A gap ends a table only if a column changes kind across it**, because in a
  sheet of text every record looks like a header.
- **A header can span two rows**; years beside a label are column names.
- **The reader says what it assumed.** The shape report had no consumer; it is
  now turned into sentences carried on the upload response. A single-sheet
  upload — the commonest case — previously had no field to carry them at all.

Every new rule was mutated away to confirm a test fails. Two mutations left the
suite green and exposed guards that were dead weight or unpinned; both were
fixed and pinned.

**Still open, deliberately.** Sheet choice (8 of the 20) is unchanged: the
reader does not have the user's question, so it cannot know which sheet was
meant. Those tests stay red rather than being quietly rewritten. The fix is to
ask, or to choose with the question in hand, not a better size heuristic. The
web UI also does not yet render the new notes.

## 6. Found on the way

- **A clean merge is not a correct merge.** A benchmark pull request was merged
  from an auto-merge commit rather than its pushed conflict resolution. The
  auto-merge kept both sides of a field rename, so `DatasetSpec` carried two
  duplicate fields; the runner read one and the suite set the other. Mainline's
  data-engineering family read 0.89 (8/9) where the resolution reads 1.00
  (9/9). Bisected across three commits; restored in a follow-up.
- **The benchmark scorecard counts only checks that ran.** A task that fails
  early removes its unrun guards from both sides of the ratio, so
  `guards 1/1 held` was printed while three guards never executed. The fix is a
  static denominator; it is not yet made.
- **Five summariser failures that looked like product defects were not.** The
  fixture stubs the coder with `lambda s: s`, which never increments the retry
  counter that bounds the loop. Production's coder increments it on all six of
  its return paths (checked by syntax tree).

### The pipeline's benchmark step could not pass

The Benchmark Scorecard step blocks every pull request, and it died on its
first task on every one of them: it installs only the `benchmark` extra, and
the runner needs SQLAlchemy and fsspec to re-publish datasets through the
sources it grades. A blocking check that cannot pass reads exactly like one
that is failing for a reason, so nobody could tell. Fixed in #485. In a clean
image all 46 runs now execute, and the step reports what it measures: nine
messy-workbook tasks failing in the **CLI's own spreadsheet reader**, the
null-word task, and one conversational check that fails by design. The nine
are the §5 defects again, in the second copy of the reader. The CLI cannot
import the platform's code, so the copies drift, and the §5 fixes do not reach
it.
