# Reliability measurements — 1.6

Measured on `develop-1.6` / `oss/1.6` with the production planning model
(`openai/gpt-oss-120b`, temperature 0.2). Every figure below was produced by
running the thing being measured, not estimated.

## Conversational routing

The reported failure: Avaloka offered seven numbered analyses, the user replied
`run 3`, and the model-training agent answered *"I can only help with
model-training and inference tasks."*

Rate at which a numbered pick was routed to the training agent instead of being
carried out, 12 trials per input. "Before" is the same tree with only the
classifier-prompt fix reverted, so the comparison isolates one change:

| user says | before | after |
| --- | ---: | ---: |
| `run 3` | 11/12 (92%) | **0/12** |
| `run 5` | 10/12 (83%) | **0/12** |
| `run 1` | 12/12 (100%) | **0/12** |
| `do 2` | 0/12 | 0/12 |
| `option 3` | 0/12 | 0/12 |
| `go ahead with 4` | 0/12 | 0/12 |

Only the word *run* was ever affected, which is why the failure presented as
intermittent rather than broken — and `_render_suggestions` closes by telling
the user to say exactly that. Genuine training requests still route correctly:
`train a model to predict score`, `build me a classifier on this data` and
`run the training plan` all reach the training agent 6/6.

A single-shot assertion would have passed most runs and been quarantined as
flaky, which is how this survived a suite that already had 18 tests for the
resolver. `tests/conversational/test_router_stability.py` asserts on a rate over
N trials with zero tolerance.

# Cross-model comparison — 1.6

Run 2026-09-20 via OpenRouter. Every figure below was produced by running the
model; nothing is estimated.

## Model ids

Both models named in the request exist and were used as-is:

| asked for | actual id | note |
| --- | --- | --- |
| Opus 4.6 | `anthropic/claude-opus-4.6` | 1M context |
| Gemma 4 | `google/gemma-4-31b-it` | 262k context; a `:free` variant also exists |
| (production default) | `openai/gpt-oss-120b` | baseline |
| (cheap control) | `openai/gpt-4o-mini` | |

## Planner routing accuracy

Nine cases x six trials = 54 routing decisions per model, against the hardened
`_classify_planner_route` prompt. Six cases must stay in planning (including
the `run N` picks that caused the reported failure), three must reach the
training agent.

| model | correct | errors | wall | cost | fails |
| --- | ---: | ---: | ---: | ---: | --- |
| `openai/gpt-oss-120b` | **54/54** | 0 | 22.0s | $0.0043 | — |
| `anthropic/claude-opus-4.6` | **54/54** | 0 | 15.7s | $0.0743 | — |
| `google/gemma-4-31b-it` | **54/54** | 0 | 15.3s | $0.0013 | — |
| `openai/gpt-4o-mini` | 48/54 | 0 | 10.8s | $0.0018 | `run the training plan` 6/6 |

Total spend: **$0.0817**.

Two things this shows. The hardened prompt is not tuned to one model -- three
capable models of very different sizes and prices all score perfectly, so the
fix generalises rather than papering over one model's quirk. And the failure is
where you would expect it: `gpt-4o-mini` misses `run the training plan` every
single time, the one case whose correct answer depends on reading "training
plan" as a noun rather than reacting to the verb "run".

On price, `gemma-4-31b-it` matched the production model exactly at **a third of
the cost**, and Opus 4.6 at 57x the price bought nothing here -- this task is
not where a frontier model earns its keep.

## The data-science benchmark cannot compare models

`python -m avaloka.benchmark run` scores 17/17, OVERALL 1.00 -- **with every
API key unset**. Verified:

```
env -u GROQ_API_KEY -u GROQ_API_KEY_PLANNING_AGENT -u GROQ_API_KEY_CODING_AGENT \
    -u OPENROUTER_API_KEY -u OPENAI_API_KEY -u GEMINI_API_KEY \
  python -m avaloka.benchmark run
  -> 17 runs, 17 passed, OVERALL 1.00
```

It never consults an LLM. **A model matrix over this benchmark would be four
identical 1.00s implying a discrimination the benchmark cannot make**, so it is
not published as one.

That is not a criticism of the suite. It is a deterministic regression harness
over the data-science code paths -- leakage detection, temporal splits,
constant columns, continuous features reaching the model -- and it is exactly
what confirmed the storage, memory-keying and ingest work changed no behaviour.
It measures Avaloka's Python, not the model behind it.

**To compare models on analysis quality**, the suite needs tasks whose answer
depends on a planning decision: an ambiguous goal where the plan can be right
or wrong, a dataset where the sensible split is not the default, a request that
should be refused as unanswerable. Until those exist, routing accuracy above is
the honest model-comparison surface, because it is the one where the model
actually decides something.
