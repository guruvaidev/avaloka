# Avaloka 2.0

**Avaloka 2.0 is the biggest release since the first open-source version.** It
turns Avaloka from a single analysis pipeline into a team of agents you can
watch working:
- the **swarm** runs in every edition;
- every agent's work is traceable, step by step;
- the planner's graph is drawn from the real data operations;
- a new **data agent** answers questions across PostgreSQL, MongoDB, SQLite
  and DuckDB at once;
- generated code runs in its own isolated executor.

It also ships the benchmark harness we use to measure all of this, with every
result reproducible from committed records.

## Highlights

- **The swarm, in every edition.** Swarm missions are no longer a paid
  feature. The open-source and free editions run up to **2 clones** per
  mission, and the cap is enforced where clones are dispatched, not in the UI.
- **See what every agent did.**
  - The agent trace API and a new agent trace page show each clone's steps,
    tools and results.
  - The planner graph is drawn from the data operations the plan actually
    performs.
  - Telemetry egress stays metadata-only: full outputs stay on your machine.
- **A data agent for questions across databases.** It answers in natural
  language across PostgreSQL, MongoDB, SQLite and DuckDB, with analytical
  specialists, a bounded plan/act/inspect loop over read-only tools, and an
  answer review that repairs before it replies.
- **Generated code is isolated.** Model-written code runs in a separate code
  executor with:
  - no route to your databases or the internet;
  - no secrets in its environment;
  - a non-root user on a read-only filesystem.

  This covers the docker quickstart and the Helm chart's analysis path. The
  exact scope is under "Generated-code isolation" below.
- **Private by default.**
  - Memory embeddings are computed locally unless you opt in to OpenAI.
  - Memory is scoped: what you ask in one conversation stays in that
    conversation.
- **Measured, not claimed.** The benchmark harness ships with its
  conversational and model-matrix tracks, a hard spend ceiling, and the 2.0
  results. See "Benchmarks" below.
- **Production-ready operations.**
  - OOM recovery and an autoscale policy.
  - Multi-architecture images (`linux/amd64`, `linux/arm64`) tagged `:2.0.0`
    and `:2.0`.
  - The Helm chart is at 2.0.0.

### Public-release facts

These are the decisions that define the public 2.0, taken on 2026-10-17:

- **The swarm is public.** Swarm missions run in every edition; the clone
  cap is enforced where clones are dispatched, and the `oss`/`free` cap is
  **2 clones** per mission (down from 3, for laptop headroom). (#510)
- **Per-clone telemetry API.** Each clone's trace is addressable through the
  agent trace API; telemetry egress stays metadata-only and full outputs stay
  local. RL trajectories are a later release. (#511)
- **Planner data graph.** The planner graph is drawn from real data
  operations rather than from a string join of step names, in the API and in
  the UI. (#511, #512)
- **DAB agents.** The DAB runtime, the analytical specialists, the legacy
  database contract and the workload optimizer ship. (#507)
- **Benchmark harness.** The harness with its conversational and
  model-matrix tracks, the spend ceiling and the guidance probes ship, and
  `benchmarks/` and `tests/benchmark/` are published. (#506)
- **Transfer credentials in direct-Ray mode.** Graph state holds connection
  handles, never credentials, and a KubeRay RayJob reads its credentials from
  a per-job Secret it owns. In direct-Ray mode (`RAY_DASHBOARD_URL` set),
  however, a transfer's environment, including its database URLs and bucket
  keys, is handed to the Ray Job Submission API, and Ray retains it with the
  job. (#599)

Withheld from the public tree until someone has run them from it:
`scripts/dab-bin/`, `scripts/setup_dab.sh`, `deploy/openclaw/skills/`
(`oss/manifest.yaml`).

## Generated-code isolation: what it covers

Code a model writes (the coder's analysis script, the validator's sample
check, a transfer's sample preview) runs in a separate **code executor**
(`app/executor`), not in the API process. The executor has no route to the
databases or the internet, no secrets in its environment (no
`DB_ENCRYPTION_KEY`, provider keys, auth secret or `REDIS_URL`), no `/state`,
and runs as a non-root user on a read-only root filesystem.

**Scope in 2.0:** this covers the docker quickstart
(`docker-compose.quickstart.yml`) and the Helm chart's analysis path
(`deploy/helm/avaloka`, `executor.enabled`, on by default) only. The following
are **not** isolated yet, so deployments that use them are not covered:

- KubeRay workers: analysis jobs routed to Ray run with the worker's network.
- The Ray/docker data-transfer runner: the generated transform runs in the
  same process as the source and destination connection strings.
- `execute_code_on_k8s` (`app/infra/python_app`): an in-process `exec()` in
  the executor pod it targets.
- The validator's sample check when no code executor is configured: it falls
  back to an in-process `exec()` in the API process, which has that process's
  full environment (`app/agents/validator.py`).
- The SSH execution path (`execution_agent_node_ssh`): generated code runs on
  the remote host with that host's environment.

A Ray-enabled or k8s-executor deployment of 2.0 runs generated code with the
same reach it had in 1.6.

## Upgrading from 1.6

- The open-source edition reported `1.0.0` from `GET /version` in 1.6 unless
  `AVALOKA_OSS_VERSION` was set. In 2.0 it reports the `VERSION` file
  (`2.0.0`); `AVALOKA_OSS_VERSION` remains an explicit override.
- Chart `version`/`appVersion` move from 1.6.0 to 2.0.0. Two values are added:
  `executor` (the code executor Deployment, its NetworkPolicies and scratch
  sizes; enabled by default; `executor.enabled=false` puts generated code back
  into the API pod: the analysis script runs in a child process with a
  scrubbed environment, but the validator's sample check runs in-process; see
  "Generated-code isolation" above) and `memory.embeddingProvider`
  (default `local`).
- **Memory embeddings are local by default.** In 1.6, `EMBEDDING_PROVIDER`
  defaulted to `auto`, which sent memory text — user queries, learned hints,
  answers, and cached schema JSON with table and column names and sample
  values — to OpenAI whenever `OPENAI_API_KEY` was set, including when that key
  was only there for chat or for a self-hosted OpenAI-spec server. 2.0 embeds
  with the bundled local model unless you opt in with `EMBEDDING_PROVIDER=openai`
  **and** `EMBEDDING_OPENAI_API_KEY`; opting in sends that memory text,
  including table and column names, to OpenAI. `auto` is deprecated and means
  `local`. Vectors an install stored with OpenAI are skipped by the Redis
  schema cache and reported once by Milvus; drop or re-embed the Milvus
  collection (see `docs/context-memory.md`).
- The `oss`/`free` swarm cap is 2 clones. A mission that asked for 3 is capped,
  not refused.

### Learned memory starts empty

- **What happens:** after the upgrade, conversations start with no learned
  memory: no remembered preferences, style signatures or learned hints. What
  1.6 stored under a bare user or session id is never read again. Cached table
  schemas are not affected.
- **Why:** memory is now scoped. What you ask for in one conversation stays in
  that conversation. Only general preferences (answer style, units, formats)
  follow you to new conversations, and facts about a dataset stay with that
  dataset. In 1.6, a fresh conversation could pick up another conversation's
  instruction: asked for the average age of stroke patients, it also returned
  the work type with the highest stroke rate.
- **Migrating preferences:** no migration script ships with 2.0, so
  preferences are re-learned as you use Avaloka. One could be written: run the
  2.0 classifier (`app/services/memory_scope.py`) over the old Chroma
  signatures and Milvus hints, and re-file only the parts it marks as
  preferences under `<user>#pref`. It is planned as a follow-up.
- **Old rows** are not deleted, and nothing reads them. Redis entries expire on
  their own within 7 days. Chroma and Milvus keep theirs. To remove them,
  delete the Chroma signature rows whose `user_id` contains no `#` and the
  Milvus insight rows whose `session_id` contains no `#`.

## Benchmarks

Every number below comes from records committed under
`benchmarks/results/2.0/`, rendered by `scripts/bench/summarize_2_0_vs_1_0.py`.
The full method, the per-cell tables, the spend and the cells that were not
run are in [`docs/benchmarks/2.0-vs-1.0.md`](../benchmarks/2.0-vs-1.0.md).

**Berkeley DataAgentBench** (54 questions over 12 datasets in four database
engines, graded by the benchmark's own validators).
- **Settings:** one trial per query, hints off, no DAB-specific prompt.
- **1.0:** not measured, because it has no multi-database agent. So the
  comparison is the 2.0 harness against the same model alone.

| Model | 2.0 harness | Same model alone |
| --- | --- | --- |
| Claude Haiku 5.5 (via OpenRouter) | **29/54 = 0.54** (95% CI 0.41–0.66) | 14/54 = 0.26 |
| gpt-oss-120b (Groq) | **12/54 = 0.22** (0.13–0.35) | 6/54 = 0.11 |

The harness roughly doubles what the same model solves on its own.
Leaderboard entries run with hints on, frontier models and five trials, so
they are not comparable trial for trial.

**Data-science suite** (synthetic ground truth, 11 task runs). 2.0 scores
**1.00**, against 0.95 for 1.0 graded by the same suite. A capable model
alone also scores 1.00 on the 7 tasks it can attempt, so this suite shows 2.0
fixing 1.0's failures, not the harness beating a strong model.

**Conversational integrity** (10 probes × 5 trials, deterministic scoring).
2.0 scores **1.00**, 1.0 scores 0.98, and models alone score 0.64–0.90. This
track does not separate 2.0 from 1.0.
